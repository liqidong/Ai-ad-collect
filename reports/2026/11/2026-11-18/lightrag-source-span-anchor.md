# LightRAG 修复位置溯源：相同文字不代表同一段原文

## 问题
固定 token 分窗会切开多字节字符。解码丢字节、生成替代符，遇到重复文本时，附近搜索能找到内容相同但位置错误的段落。引用高亮因此可能看似正确却指错来源。

## 输入
原始文本、tokenizer、分窗大小/重叠与可选分隔符；需请求 source span 才走位置映射分支。

## 输出
原有 chunk 文本与顺序；可信时附原文字符区间，歧义时不提供区间。它不生成新的答案质量保证。

## 流程
### 1. 建立可验证锚点
输入一个文本分段及 token 序列，以已知 token/字符位置为起点。开头空白被 tokenizer 丢弃的情况，以完整解码与原文后缀核对后调整起点。

### 2. 联合解码定位
从已验证锚点解码到窗口末尾；确认联合文本匹配原文且窗口是它的后缀，再推算区间。用位置证据替代“附近能搜到同样文字”。

### 3. 保守处理歧义
源文本含真实 U+FFFD 时，窗口边缘替代符要做 token 往返检查；不确定就不输出位置。无真实替代符时才尝试多字节边界内部文本恢复。锚点失真后停止该段溯源，而不改变 chunk 内容。

### 4. 下游验证
测试覆盖块加载、再次硬分块、sidecar 回填和入库存储。工程验收应确认引用仍落在正确原文位置，同时明确记录没有位置的 chunk，不能以空结果冒充修复成功。

## 机制
改动的核心是“内容相等”不足以证明“位置相等”。联合解码保留窗口与已知锚点的关系，避免重复文字造成假阳性；宁可降低可标注覆盖率，也不编造精确位置。代码中的 source span 是字符偏移，测试的字节真值用于独立核对，不能混用两种单位。

## 局限与未知
- 未复现测试或跑真实文档集；合成测试不证明任意 tokenizer 均有完整溯源覆盖。
- 无法证明位置时省略 source span 是设计行为；使用方需决定如何显示“无精确定位”的引用。
- 修复不自动重建已入库数据，也没有提供 RAG 回答准确率提升、召回率或生产延迟数据。

## 工程建议（未实测）
- 工程判断：对需要点击引用回到原文的中文或多语言知识库，这类定位可靠性值得单独验收。普通问答是否改善仍需另测，不应把引用定位修复包装成检索算法提升。
- 建议建立公开合成语料：重复段落、emoji、真实替代符、前导空白及有损 tokenizer。分别统计有效 span 精度、span 覆盖率、chunk 文本是否变化；先明确字符与字节单位。
- 建议做一次完整入库回读验收，检查引用页/块与精确区间是否仍对应同一来源。若升级版本仍未包含该提交，先在隔离分支验证，不直接混用主分支生产依赖。
