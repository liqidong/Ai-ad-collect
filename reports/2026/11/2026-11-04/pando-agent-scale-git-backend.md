# Pando：为大量并行 Agent 重做 Git 后端，开放的是客户端改进而非服务端

来源日期：技术文章2026-11-02；作者称2026年4月开始生产；补丁跟踪页2026-10-31；公开codex分支提交时间2026-10-19，非今日新代码

核查时间：2026-11-04T00:09:05Z

状态：新公开工程案例；内部生产／服务端未公开；Git部分改进公开

## 核心问题

这是代码仓库基础设施，不是模型训练或推理算法。问题是许多编码Agent同时写分支、CI反复读取同一提交时，仓库服务端的协调、解包和重复打包成为瓶颈。传统全库排序会让互不相关的分支相互阻塞；为每个客户端重新生成最小数据包又难以复用缓存。新意是调整一致性与传输冗余的取舍，而非发明新的Git命令。

## 训练与推理输入

没有训练数据输入或模型权重。写路径接收Git客户端生成的packfile（提交、树和文件内容对象的压缩集合）、目标分支、期望旧版本及依赖历史；读路径接收客户端已有提交haves和所需提交wants。运行依赖对象存储、支持事务的元数据存储、区域缓存和具备相应Git协议支持的客户端。

## 输出与资产形式

写路径产生不可变对象包、带依赖关系的分支版本记录及更新后的分支指针；读路径返回可下载的packfile URI，客户端重建请求提交的完整对象图。产物仍是可由Git读取的代码历史，不是新模型、不自动解决代码语义冲突。

## 分步流程

### 1. 明确共享基线，生成可复用包

输入是本地更改与服务端公布的历史基线。以主干作为有限的共同依赖，客户端压缩本次分支所需对象；输出包可能比最小增量大，却更容易被其他已有该主干的客户端复用。反复推同一分支可能重复发送主干之外的历史。

### 2. 接收对象与发布分支版本

输入packfile流经校验后存入blob存储，元数据事务关联新分支版本、旧依赖和包位置，并检查和更新分支指针。输出是可被读取的新提交；并发改同一指针仍须竞争，不能把“不同分支并行”误解为无冲突写入。

### 3. 将已有/所需提交转成包依赖

读取者报告haves和wants。服务端查提交到分支版本的映射，补齐缺少的历史依赖，输出能覆盖所需对象的一组已存包，而非为每位读取者再次压缩整个差集。

### 4. 下载、索引与连通性检查

Git协议v2的packfile-uris能力让服务端给出独立下载地址。客户端必须取回并索引全部所需包后再检查对象连通性。公开文档说明，通常按顺序索引以满足跨包REF_DELTA依赖；只有服务器给出且客户端请求no-ref-delta保证时才能并行索引并拒绝违反保证的包。

### 5. 后台合并细碎历史

小包累计会导致一次追赶需要下载过多文件。后台把相邻版本覆盖范围分层合并成更大包，让读请求选择较少的覆盖集合；这缓解请求数量和元数据查找开销，但并非免费操作，仍要支付压缩、存储与缓存资源。

## 关键机制

作者架构把“分支指针的可变状态”和“不可变对象数据”分离，并允许跨分支视图来自不同时间，换取无关分支独立扩展。公开Git文档提供可检查的客户端约束：packfile-uris需要protocol v2；fetch.uriprotocols默认空，必须与服务端能力协商；认证按包URL目的地主机查找，不能把谈判请求的凭据直接转发到任意下载地址。缓存能减少相同字节的重复计算，但不会减少所有网络字节。更换客户端本身不保证GitHub或其他服务端支持相同策略。

- 作者内部生产结果：推送延迟下降：部署章节报告中位push延迟降低近80%，并称单小时服务超过57 TB包数据、超过99%字节来自本地磁盘缓存。未给出可下载生产日志、固定硬件成本表或独立对照；文章无论文式表号。 [原始证据](https://openai.com/index/scaling-git-at-openai/#deploying-pando)
- 作者带宽测试，不是编码质量评测：读取性能章节称标准云虚拟机的clone/fetch可跑满10 Gbps链路。指标方向是吞吐更高，但没有任务成功率、代码正确性或端到端开发时间对照。 [原始证据](https://openai.com/index/scaling-git-at-openai/#line-rate-fetch-and-clone-performance)
- 比较图明确属于合成教学模拟：网页设置1000客户端选择不同分支反复推送，说明push-to-fetch含重试和读者等待、不含构建测试；页面明示不是生产benchmark。本次未执行交互模拟，不报告图中数值。 [原始证据](https://openai.com/index/scaling-git-at-openai/#comparing-approaches)
- 公开客户端协议约束可检查：固定提交文档明确v2协商、索引顺序、no-ref-delta并行条件、认证目标以及502/503/504最多两次重试等行为。该文档不是Pando服务端源码，也不能作为所有上游Git版本均支持的证据。 [原始证据](https://github.com/openai/git/blob/9fe64f46bdef176eabbc4e7f1f15c8e4f8dbc325/Documentation/technical/packfile-uri.adoc)

## 工程建议，非复现实验

- 工程判断：先测现有流水线的模型时间、Git传输/排队时间、构建测试时间，确认瓶颈再考虑重构；少量个人Agent可能不值得承担后端复杂性。
- 最小可做验证：在独立测试仓记录固定提交的冷/热clone与fetch耗时、传输字节、失败重试；检查客户端和服务端的packfile URI支持。若服务端不支持，止于基线测试，不将协议配置当现成Pando。
- 权限建议：对象下载URL必须做目的地主机约束，凭据按主机隔离；仓库权限、分支保护、审查与CI门禁不能因为缓存或并行写入被绕过。此为工程建议，非已测系统保证。
- Harness设计借鉴：任务结果绑定不可变commit ID而非仅分支名；跨Agent共享状态明确版本与依赖，更新同一分支时保留冲突检测。取消任务不等于撤销已经成功的push，应记录副作用并核验后续状态。
- 评测建议：分别统计push确认、另一个Agent可读取提交的延迟、缓存命中率和重复传输，另行测真实任务通过率。不能把基础设施延迟缩短直接折算成模型能力提升。
