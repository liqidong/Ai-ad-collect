# MarkItDown 0.1.8：异构文件如何统一成 Markdown

核查范围：已阅读发布说明、官方 README、v0.1.8 核心转换路由及 OCR 插件说明；发布时间从官方发布页 relative-time 的 datetime 属性核实。未安装、未运行转换或准确率测试；当前主分支 README 用于一般用途说明，具体 OCR 与路由对照版本标签。

## 解决什么问题

一个知识库可能同时收到 Word、幻灯片、表格、PDF 与压缩包。逐种编写解析代码成本很高，直接复制纯文本又会丢掉标题、列表和表格关系。MarkItDown 提供统一转换入口，面向文本分析与模型输入。0.1.8 是兼容性和稳定性修补集合，发布于 2026-09-21 21:22:51 UTC。

## 输入

输入可以是本地文件、二进制流或 URL。格式覆盖 Office、PDF、HTML、CSV、EPUB 等，但具体支持取决于依赖和配置。使用 OCR 或云分析时，还需要显式启用相应能力并提供服务配置；不能理解成所有文件默认都由视觉模型解析。

## 输出

主要输出为 result.markdown 中的文本，可保留标题、列表、链接和表格表达，适合分块、搜索与后续问答。它不承诺复原原文件版式，也不等同于计算工作簿公式、完整还原幻灯片视觉布局或验证文档事实。

## 完整流程

### 1. ① 把输入变成可识别的文件流

统一入口根据输入类型进入本地、流或网络读取路径，并结合扩展名、响应元数据与内容识别构建格式候选。扩展名只是线索，解析器仍需判断自己能否接收该内容。

### 2. ② 按优先级选择专用转换器

源码中的 _convert 对已注册转换器排序，再调用 accepts 判断适配性；可接受时执行转换，记录失败尝试。这样 Word、表格和 HTML 能共用外层入口，却保留各自的结构处理逻辑。

### 3. ③ 先处理原生内容，再按需补充图中文字

OCR 插件注册较高优先级的增强转换器。Office 路径复用核心转换，提取嵌入图片后交给视觉模型识别，将识别结果插回文档结构，再转为 Markdown；PDF 则使用单独路径。

### 4. ④ 检查转换覆盖率，再交给下游

工程上应对照源文件检查段落、表格列与图片文字。比如一张带截图的会议幻灯片，成功返回文本并不意味着截图也被识别。建议保存文件标识、版本、转换设置与异常记录，支持后续定位缺失。

## 核心机制

核心机制是“格式路由＋专用转换器＋统一文本结果”，而不是单一端到端模型。OCR 插件启用后将嵌入图片发给配置的模型；扫描 PDF 可将整页渲染后识别。若未提供 llm_client，插件会跳过 OCR；单张图片调用失败也可能继续生成其余内容，因此成功状态不能代替完整性检查。

## 限制与未核实项

- 这是面向机器读取的有损转换。复杂布局、图片位置与表格换行可能无法完整表达，不能把 Markdown 当作原始文件的法律或视觉替代品。

- OCR 取决于所选模型，可能遗漏或误识别文字；需要额外成本，也可能向外部服务发送文档图像。

- 文件和 URL 读取继承当前进程权限。转换器不是文件沙箱，也不是不可信 URL 的安全网关。

## 工程判断与下一步

- 建议按格式建立小型回归集，优先检查 CSV 列数、公式文本、幻灯片阅读顺序、空标题与图片文字，不以“没有报错”作为唯一验收。

- 接收上传文件时采用最窄的流转换入口；限制大小、类型、运行时间与资源权限。需要外部模型或云服务时先确认数据使用授权。

- 若与网页采集组合，可让采集器处理网页，让 MarkItDown 处理下载附件；两者都保留原件与来源，后续再统一分块。此为应用建议，未实施安装。
